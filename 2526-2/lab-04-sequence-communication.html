1.
Từ business thinking sang runtime thinking

Buổi trước ta đã có gì?

Behavior Diagram ở W3

  • Use Case Diagram: hệ thống cần làm gì cho actor?
  • Activity Diagram: quy trình nghiệp vụ đi qua các bước nào?
  • Tập trung vào mục tiêu người dùng và workflow.

Business thinking

  • Góc nhìn nghiệp vụ tập trung vào người dùng.
  • Tập trung vào mục tiêu và quy trình công việc.
  • Chưa đi sâu vào lập trình hoặc cấu trúc bên trong.

Mục tiêu tuần 4

Chuyển từ câu hỏi hệ thống phải làm gì? sang hệ thống thực hiện điều đó như thế nào trong quá trình thực thi?

Runtime thinking

  • Nhìn hệ thống khi đang chạy.
  • Quan sát object nào gọi object nào.
  • Theo dõi message và thứ tự xử lý.

Hai biểu đồ chính

  • Sequence Diagram: nhấn mạnh thời gian.
  • Communication Diagram: nhấn mạnh cộng tác giữa object.
  • Cả hai đều thuộc UML Interaction Diagram.

Từ use case đến interaction

Use Case / Activity

→

Sequence / Communication

Mô tả object tham gia, message được gửi và cách interaction diễn ra khi chạy.

2.
Sequence Diagram

Sequence Diagram là gì?

Định nghĩa
Sequence Diagram là một UML Interaction Diagram mô tả cách các đối tượng tương tác với nhau theo thứ tự thời gian thông qua việc trao đổi message.
  • Thể hiện các đối tượng tham gia trong một kịch bản.
  • Thể hiện các message được gửi giữa các đối tượng.
  • Thể hiện thứ tự thời gian của các tương tác.

Thành phần chính

Thành phần Mô tả Khi đọc cần hỏi
Actor Thực thể bên ngoài hệ thống tương tác với hệ thống. Ai kích hoạt kịch bản?
Lifeline Sự tồn tại của một participant trong suốt interaction. Participant sống trong khoảng nào?
Activation Khoảng thời gian một phần tử đang thực hiện thao tác. Object đang xử lý message nào?
Note Nhận xét hoặc giải thích gắn vào phần tử. Có giả định hoặc điều kiện cần ghi không?
Message Thông điệp gửi giữa các đối tượng. Ai gọi ai, theo thứ tự nào?

Ký hiệu sequence cơ bản

Thời gian đọc từ trên xuống dưới; lifeline xếp theo chiều ngang.

Các loại message

Loại message Ý nghĩa
Call message Kích hoạt một operation trên lifeline đích.
Synchronous message Caller chờ receiver xử lý xong rồi mới tiếp tục.
Asynchronous message Caller gửi message và có thể tiếp tục xử lý mà không chờ kết quả ngay.
Return message Thông điệp trả kết quả về nơi gọi.
Create message Tạo một đối tượng mới trong quá trình tương tác.
Self message Một đối tượng gửi message cho chính nó để gọi xử lý nội bộ.
Destroy message Kết thúc vòng đời của một đối tượng.
Duration message Biểu diễn khoảng thời gian cần để thực hiện một hành động hoặc interaction.

Combined fragments

alt

Alternative: nhiều nhánh điều kiện.

opt

Optional: nhánh tùy chọn.

loop

Lặp lại một đoạn interaction.

par

Parallel: các luồng song song.

ref

Tham chiếu sang interaction khác.

region

Vùng logic trong interaction.

neg

Negative: trace không hợp lệ.

sd

Frame của sequence/interaction diagram.

Tại sao cần Sequence Diagram?

Hiểu luồng xử lý

Theo dõi thứ tự message khi hệ thống chạy.

Hiện thực use case

Chuyển use case thành interaction giữa các object.

Thiết kế interaction

Làm rõ thành phần nào gọi thành phần nào.

Phát hiện vấn đề

Nhìn sớm logic thiếu, vòng lặp sai hoặc dependency lạ.

Giao tiếp nhóm

Developer, tester và stakeholder kỹ thuật cùng đọc được.

Tài liệu hóa

Lưu lại runtime behavior của các kịch bản quan trọng.

Khi nào dùng Sequence Diagram?

Phân tích use case

  • Khi phân tích hoặc hiện thực hóa một use case.
  • Khi cần mô tả tương tác giữa các đối tượng.

Thiết kế logic xử lý

  • Khi thiết kế logic xử lý của hệ thống.
  • Khi cần mô tả thứ tự các bước xử lý.

Cách vẽ Sequence Diagram

Bước Việc cần làm
1. Xác định kịch bản Chọn một use case hoặc tình huống cụ thể cần mô tả.
2. Xác định participant Liệt kê actor, hệ thống hoặc object tham gia interaction.
3. Tạo lifeline Vẽ đường sống cho mỗi participant.
4. Sắp xếp lifeline Đặt participant theo chiều ngang để dễ quan sát luồng tương tác.
5. Vẽ message Dùng mũi tên biểu diễn message giữa các đối tượng.
6. Thêm activation Thể hiện khoảng thời gian object đang xử lý message.
7. Thêm điều kiện/lặp Dùng combined fragments như alt, opt, loop.
8. Kiểm tra Đảm bảo logic đúng, dễ hiểu, thêm note nếu cần.

Nguyên tắc BCE để xác định object

Boundary

Đối tượng giao tiếp với actor: UI, API endpoint, form, screen.

Control

Đối tượng điều khiển logic của use case hoặc orchestration.

Entity

Đối tượng dữ liệu, domain model hoặc persistence model.

Khi bí participant, bắt đầu từ actor rồi tìm Boundary, Control, Entity cho kịch bản đó.

Ví dụ từ Lab 02: Online Bookshop

  • Online customer search book catalog.
  • Customer xem mô tả của sách được chọn.
  • Customer add book to shopping cart.
  • Checkout được tách thành interaction tham chiếu.

3.
Communication Diagram

Communication Diagram là gì?

Định nghĩa
Communication Diagram là một UML Interaction Diagram mô tả cách các đối tượng tương tác với nhau thông qua việc gửi message trong một kịch bản.
  • Nhấn mạnh object nào liên kết với object nào.
  • Nhấn mạnh collaboration để thực hiện một chức năng.
  • Thứ tự message được thể hiện bằng số thứ tự.

Thành phần chính

Thành phần Mô tả Khi đọc cần hỏi
Objects Các đối tượng tham gia interaction, thường biểu diễn bằng hình chữ nhật. Object nào tham gia use case?
Links Đường nối giữa object, thể hiện quan hệ cho phép gửi message. Object nào có thể giao tiếp trực tiếp?
Messages Mũi tên biểu diễn message từ object gửi đến object nhận. Message nào được gửi qua link?
Sequence Numbers Số thứ tự như 1, 2, 1.1, 1.2 để thể hiện thứ tự message. Message nào xảy ra trước/sau?

Ví dụ từ Lab 02: Communication Diagram

  • Web Customer gửi find_books().
  • Online Bookshop gọi Inventory, Book, Shopping Cart và Order.
  • Số thứ tự message thể hiện trình tự.
  • Các điều kiện như [interested] gắn trên message.

Tại sao cần Communication Diagram?

Collaboration

  • Mô tả cách object cộng tác để thực hiện chức năng.
  • Mô hình hóa message passing trong use case.

Thiết kế kiến trúc

  • Phân tích cơ chế collaboration trong thiết kế kiến trúc.
  • Xác định object và operation cần thiết trong hệ thống.

Khi nào dùng Communication Diagram?

Khi cần thấy cấu trúc

  • Phân tích sự cộng tác giữa object trong một kịch bản.
  • Muốn thấy rõ quan hệ giữa object và cách chúng kết nối.
  • Thiết kế hoặc kiểm tra cấu trúc interaction giữa các thành phần.

Khi kiểm tra use case

  • Phân tích object cần thiết trong một use case.
  • Phân tích cách object giao tiếp.
  • Chuyển đổi từ sequence diagram để xem collaboration structure.

4.
So sánh và thực hành

Hai diagram có ý nghĩa tương đương

Cùng interaction

Cùng mô tả một interaction giữa các object trong một kịch bản.

Cùng thông tin

Cùng chứa thông tin về message và object.

Có thể chuyển đổi

Có thể chuyển qua lại khi cần đổi góc nhìn.

Điểm khác nhau nằm ở cách tổ chức thông tin: thời gian hay cấu trúc cộng tác.

Sequence Diagram vs Communication Diagram

Tiêu chí Sequence Diagram Communication Diagram
Mục đích chính Mô tả thứ tự message theo thời gian giữa các đối tượng. Mô tả quan hệ và cấu trúc giao tiếp giữa các đối tượng.
Cách tổ chức biểu đồ Sắp xếp theo thời gian. Mô tả quan hệ và cấu trúc giao tiếp giữa các đối tượng.
Đánh số message Không bắt buộc. Bắt buộc.
Ứng dụng chính Mô tả runtime behavior của use case. Phân tích collaboration giữa các object.
Mức độ dùng thực tế Rất phổ biến. Ít dùng hơn.

Thực hành 1: Place Order

Kịch bản: khách hàng đặt hàng, hệ thống kiểm tra giỏ hàng, kiểm tra tồn kho, xử lý thanh toán và tạo đơn hàng.

Sequence diagram

  • Chọn participant theo BCE.
  • Thể hiện message theo thứ tự thời gian.
  • Dùng alt nếu payment thất bại hoặc hết hàng.

Communication diagram

  • Giữ cùng object và message.
  • Vẽ link giữa object có trao đổi message.
  • Đánh số message bắt buộc.

Gợi ý participant cho Place Order

Boundary

  • Customer
  • Checkout UI / API

Control

  • Order Controller
  • Payment Service
  • Inventory Service

Entity

  • Shopping Cart
  • Order
  • Product / Stock

Thực hành 2: Library Item Overdue

Kịch bản: hệ thống thư viện phát hiện item quá hạn, thông báo cho người mượn, tính phí phạt nếu cần và cập nhật trạng thái.

Sequence diagram

  • Thể hiện scheduler hoặc librarian kích hoạt kiểm tra.
  • Dùng loop cho nhiều loan/item.
  • Dùng opt/alt cho nhắc hạn hoặc tính phí.

Communication diagram

  • Vẽ quan hệ giữa Loan, Member, Notification, Fine.
  • Đánh số message như 1, 1.1, 1.2.
  • Kiểm tra object nào thực sự cần operation.

Yêu cầu nộp bài

Bắt buộc

  • 01 sequence diagram cho Place Order hoặc Library Item Overdue.
  • 01 communication diagram cho cùng kịch bản.
  • Hai diagram phải giữ cùng object và message chính.

Mỗi diagram cần kèm

  • 1-2 câu mô tả kịch bản.
  • Danh sách participant theo BCE nếu dùng.
  • Giải thích fragment hoặc số thứ tự message quan trọng.

Checklist tự kiểm tra

Sequence

  • Thời gian đọc từ trên xuống có rõ không?
  • Lifeline có đúng actor/object tham gia không?
  • Activation và fragment có dùng đúng chỗ không?
  • Message name có giống operation/action không?

Communication

  • Mọi message có sequence number không?
  • Các object gửi message có link nối không?
  • Số thứ tự có thể map lại sang sequence diagram không?
  • Diagram có làm rõ collaboration structure không?
