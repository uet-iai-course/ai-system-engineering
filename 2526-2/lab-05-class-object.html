2.
Class Diagram

Class Diagram là gì?

Định nghĩa
Class Diagram là một UML Structural Diagram mô tả cấu trúc tĩnh của hệ thống bằng cách hiển thị các lớp, thuộc tính, phương thức và mối quan hệ giữa chúng.
  • Thể hiện các thành phần cốt lõi cấu tạo nên hệ thống.
  • Thể hiện dữ liệu và hành vi của từng thành phần.
  • Thể hiện các quy tắc liên kết và cấu trúc tĩnh giữa các lớp.

Ký hiệu class cơ bản

MyClass
+ attribute1 : int
- attribute2 : float
# attribute3 : Circle
+ op1(in p1 : bool, in p2) : String
- op2(input p3 : int) : float
# op3(out p6) : Class6*
  • Class: thực thể chính của hệ thống.
  • Attribute: dữ liệu class nắm giữ.
  • Method: hành vi hoặc thao tác xử lý của class.
  • Ba khoang thường dùng: tên, thuộc tính, phương thức.

Thành phần chính

Thành phần Mô tả Khi đọc cần hỏi
Class Thực thể chính, thường biểu diễn bằng hình chữ nhật chia 3 phần. Lớp này đại diện cho khái niệm miền hay service nào?
Attribute Thuộc tính hoặc dữ liệu mà class nắm giữ. Lớp cần giữ trạng thái gì?
Method Hành vi hoặc thao tác xử lý của class. Lớp nhận message nào và xử lý ra sao?
Relationship Mối quan hệ giữa các class. Các class phụ thuộc, sở hữu hay kế thừa nhau?
Multiplicity Bản số xác định số lượng object tham gia liên kết. Một object ở đầu này liên quan đến bao nhiêu object ở đầu kia?

Các loại relationship

Dependency

Mũi tên nét đứt.

Client --> Service

Association

Đường nét liền.

Order - Payment

Aggregation

Hình thoi rỗng.

Whole-part lỏng.

Composition

Hình thoi đặc.

Whole-part chặt.

Inheritance

Mũi tên tam giác rỗng.

Subclass -|> Superclass

Relationship trong PDF W5

Quan hệ Ký hiệu Ý nghĩa
Dependency Mũi tên nét đứt Một class sử dụng hoặc phụ thuộc tạm thời vào class khác.
Association Đường nét liền Quan hệ kết hợp hoặc biết nhau giữa các class.
Aggregation Đường nét liền, hình thoi rỗng Quan hệ tập hợp; phần vẫn có thể tồn tại độc lập.
Composition Đường nét liền, hình thoi đặc Quan hệ cấu thành; phần phụ thuộc vòng đời vào toàn thể.
Inheritance Mũi tên tam giác rỗng Quan hệ kế thừa giữa superclass và subclass.

Multiplicity

  • 1: đúng một object.
  • 0..1: không có hoặc có một object.
  • * hoặc 0..*: nhiều object, có thể bằng 0.
  • 1..*: ít nhất một object.

Tại sao cần Class Diagram?

Kiến trúc tĩnh

Nắm bắt cấu trúc tĩnh và kiến trúc lớp của hệ thống.

Nền cho code OOP

Lập trình viên dùng class, attribute, method làm base để viết code.

Nền cho database

Định hình cấu trúc dữ liệu trước khi thiết kế bảng và quan hệ.

Phát hiện lỗi thiết kế

Nhìn ra class quá nhiều trách nhiệm, quan hệ sai hoặc multiplicity thiếu.

Giao tiếp nhóm

Developer, tester và người thiết kế domain cùng có một bản đồ cấu trúc.

Tài liệu hóa

Lưu lại cấu trúc hệ thống để bảo trì và onboarding.

Khi nào dùng Class Diagram?

Phân tích và thiết kế

  • Khi phân tích hoặc thiết kế cấu trúc hệ thống mới.
  • Khi cần mô tả cấu trúc dữ liệu và hành vi của object.

Chuẩn bị triển khai

  • Khi thiết kế nền tảng để viết code OOP.
  • Khi cần mô tả quan hệ giữa các thành phần.

Cách vẽ Class Diagram

Bước Việc cần làm
1. Xác định class Từ các lifeline trong Sequence Diagram, suy ra các class tương ứng.
2. Xác định method Dựa vào message trỏ vào lifeline, tạo method cho class nhận.
3. Xác định attribute Xác định dữ liệu cần để thực hiện method và duy trì trạng thái.
4. Thêm relationship Xác định cách class liên kết: dependency, association, aggregation, composition, inheritance.
5. Xác định multiplicity Đặt quy tắc số lượng object tham gia liên kết.
6. Tách responsibility Dùng SOLID/SRP để chia nhỏ class ôm đồm quá nhiều việc.
7. Kiểm tra và hoàn thiện Refactor design để đảm bảo tối ưu, thêm note nếu cần.

Từ Sequence Diagram sang Class Diagram

Lifeline → Class

Mỗi participant ổn định trong sequence có thể trở thành một class hoặc component.

Incoming message → Method

Message đi vào lifeline gợi ý method mà class nhận cần cung cấp.

State → Attribute

Dữ liệu cần nhớ giữa các bước xử lý trở thành attribute hoặc entity field.

Đây là cầu nối quan trọng giữa W4 và W5: từ hành vi runtime suy ra cấu trúc tĩnh.

SOLID/SRP khi kiểm tra class

SRP: một class nên chỉ có một lý do để thay đổi.

Dấu hiệu cần tách

  • Tên class có chữ Manager/Util quá chung.
  • Class phục vụ nhiều actor khác nhau.
  • Method trải rộng qua UI, business logic và persistence.

Cách refactor

  • Tách class theo trách nhiệm.
  • Giữ domain model tập trung vào dữ liệu và quy tắc miền.
  • Đưa orchestration sang control/service class.

3.
Object Diagram

Object Diagram là gì?

Định nghĩa
Object Diagram là một UML Structural Diagram hiển thị một snapshot instance của cấu trúc tĩnh hệ thống tại một thời điểm cụ thể trong quá trình thực thi.
  • Hiển thị object cụ thể đang tồn tại tại runtime.
  • Hiển thị giá trị thuộc tính cụ thể của object.
  • Hiển thị link giữa các object tại thời điểm chụp.

Ký hiệu object cơ bản

order12 : Order
number = "12"
status = "Confirmed"
total = 850000
  • Object: đối tượng cụ thể đang tồn tại.
  • Tên thường được gạch chân: obj : ClassName.
  • Attribute values: slot có giá trị tại thời điểm chụp.
  • Object diagram không liệt kê method như class diagram.

Thành phần chính

Thành phần Mô tả Khi đọc cần hỏi
Object Đối tượng cụ thể đang tồn tại, ví dụ obj : ClassName. Đây là instance nào của class nào?
Attributes & Values Thuộc tính đi kèm giá trị cụ thể, ví dụ status = "Active". Snapshot này đang ghi lại trạng thái gì?
Links Đường nối giữa object, hiện thực hóa association trong runtime. Object nào đang liên kết trực tiếp với object nào?

Links: relationship ở runtime

Class Diagram nói có association; Object Diagram cho biết hiện tại object nào đang nối với object nào.

Tại sao cần Object Diagram?

Runtime snapshot

  • Mô tả cấu trúc dữ liệu phức tạp tại lúc chạy.
  • Cho ví dụ thực tế khi class diagram quá trừu tượng.

Validate design

  • Kiểm chứng bản thiết kế class diagram.
  • Kiểm tra tính đúng đắn của multiplicity.

Khi nào dùng Object Diagram?

Validate cấu trúc

  • Cần validate class diagram và quy tắc liên kết.
  • Muốn kiểm multiplicity bằng một ví dụ cụ thể.

Giải thích runtime

  • Muốn thấy trạng thái và dữ liệu object tại một thời điểm.
  • Cung cấp runtime example cho cấu trúc phức tạp.
  • Phân tích sự hình thành object trong một use case.

Ví dụ từ Lab 02: Object Diagram

  • Object diagram mô tả trạng thái cụ thể tại runtime.
  • loginCtrl là instance của Login Controller.
  • Slot lưu giá trị cụ thể như attemptLimit, lockoutTime, URI login/logout.

Phân tích object diagram mẫu

Chi tiết Cách đọc
loginCtrl Instance của Login Controller với các slot Integer/String cụ thể.
User Manager, Cookie Manager, Logger Các object liên quan trực tiếp đến quá trình login.
Hibernate User DAO DAO được User Manager dùng để tìm user theo loginID hoặc email.
defaultURIs Collection 5 String có thứ tự và unique.
Link không navigable backward Đọc được hướng biết/gọi giữa các object ở thời điểm chụp.

4.
So sánh và thực hành

Hai diagram bổ trợ cho nhau

Cùng hệ thống tĩnh

Cùng mô tả cấu trúc của một hệ thống, nhưng ở hai mức khác nhau.

Khuôn mẫu và sản phẩm

Class Diagram là khuôn mẫu; Object Diagram là sản phẩm instance từ khuôn mẫu.

Đối chiếu qua lại

Có thể dùng object snapshot để kiểm chứng class, multiplicity và quan hệ.

Điểm khác nhau nằm ở cách tổ chức thông tin: class/rule hay object/state.

Class Diagram vs Object Diagram

Tiêu chí Class Diagram Object Diagram
Mục đích chính Mô tả cấu trúc, quy tắc và khuôn mẫu của hệ thống. Mô tả trạng thái của hệ thống tại một thời điểm thực thi.
Cách tổ chức biểu đồ Mô tả quan hệ giữa các lớp. Mô tả quan hệ thực tế giữa các đối tượng.
Thành phần chính Class, Attribute, Method. Object, Attribute Values.
Ứng dụng chính Thiết kế kiến trúc, làm base cho code OOP. Validate thiết kế: snapshot, runtime example.
Mức độ dùng thực tế Rất phổ biến. Ít dùng hơn, thường dùng để test/validate.

Thực hành 1: GUI Drawing Application

Thiết kế class diagram cho ứng dụng vẽ hình đơn giản: người dùng có thể tạo, chọn, di chuyển, thay đổi màu và lưu bản vẽ.

Yêu cầu class diagram

  • Có class cho Canvas, Shape, Tool và Drawing.
  • Có ít nhất 3 loại shape cụ thể.
  • Thể hiện inheritance và composition/aggregation.

Cần ghi rõ

  • Attribute chính của Shape: vị trí, màu, kích thước.
  • Method chính: draw(), move(), resize().
  • Multiplicity giữa Drawing, Canvas và Shape.

Gợi ý model cho GUI Drawing

Core domain

  • Drawing
  • Canvas
  • Shape
  • Layer

Shape hierarchy

  • Rectangle
  • Circle
  • Line
  • TextShape

Interaction helpers

  • DrawingTool
  • SelectionTool
  • ColorPalette
  • FileStorage

Thực hành 2: Order Management System

Từ class diagram rút gọn cho hệ thống quản lý đơn hàng, tạo một object diagram cho một đơn hàng cụ thể tại thời điểm checkout thành công.

Class diagram cần có

  • Customer, Account, Order, LineItem, Product, Payment.
  • Relationship và multiplicity giữa các class.
  • Ít nhất một composition hợp lý.

Object diagram cần có

  • Một customer cụ thể và một order cụ thể.
  • Ít nhất 2 line item với product khác nhau.
  • Payment đã có trạng thái thành công.

Yêu cầu nộp bài

Bắt buộc

  • 01 class diagram cho GUI Drawing Application hoặc Order Management System.
  • 01 object diagram snapshot tương ứng nếu chọn Order Management.
  • Ghi rõ multiplicity trên các association quan trọng.

Mỗi diagram cần kèm

  • 1-2 câu mô tả phạm vi bài toán.
  • Danh sách class/object chính.
  • Giải thích 2 relationship hoặc slot quan trọng.

Checklist tự kiểm tra

Class

  • Class có tên là danh từ miền không?
  • Attribute/method có nằm đúng class không?
  • Relationship có đúng loại không?
  • Multiplicity có đủ trên association quan trọng không?
  • Có class nào vi phạm SRP rõ ràng không?

Object

  • Tên object có dạng obj : ClassName không?
  • Slot có giá trị cụ thể tại thời điểm chụp không?
  • Link có map được sang association trong class diagram không?
  • Snapshot có validate được multiplicity không?

Tổng kết Lab 05

Hôm nay cần nhớ

  • Class Diagram mô tả cấu trúc, quy tắc và khuôn mẫu của hệ thống.
  • Object Diagram mô tả snapshot object tại một thời điểm thực thi.
  • Relationship và multiplicity là phần quan trọng nhất khi đọc class diagram.
  • SOLID/SRP giúp kiểm tra class có đang ôm quá nhiều trách nhiệm không.
