Từ OOP thinking sang architecture thinking

Buổi trước ta đã có gì?

Structural Diagram ở W5

  • Class Diagram: cấu trúc, quy tắc và khuôn mẫu của hệ thống.
  • Object Diagram: snapshot object tại một thời điểm thực thi.
  • Tập trung vào đối tượng, dữ liệu và mối quan hệ.

OOP thinking

  • Góc nhìn cấu trúc, mang tính tĩnh.
  • Nhìn các thực thể cốt lõi trong miền bài toán.
  • Câu hỏi chính: hệ thống được cấu tạo từ những thành phần cốt lõi nào?

Mục tiêu tuần 6

Chuyển từ cấu trúc OOP sang câu hỏi: hệ thống được chia thành các thành phần lớn nào và triển khai như thế nào?

Structural Diagram

  • Component Diagram: module lớn và interface.
  • Deployment Diagram: node, artifact, hạ tầng và kết nối.
  • Cả hai cùng phục vụ thiết kế kiến trúc.

Architecture thinking

  • Góc nhìn kiến trúc tổng thể.
  • Tập trung vào cách hệ thống được chia thành module lớn.
  • Tập trung vào cách module chạy trên hạ tầng thực tế.

2.
Component Diagram

Component Diagram là gì?

Tổng quan
Component Diagram là một sơ đồ kiến trúc trong UML dùng để mô tả các module lớn trong hệ thống, mối quan hệ giữa các module và phụ thuộc giữa các thành phần.
  • Thể hiện các thành phần hệ thống.
  • Thể hiện interface giữa các thành phần.
  • Thể hiện quan hệ phụ thuộc giữa các module.

Thành phần chính

Thành phần Mô tả Ví dụ trong hệ thống AI
Component Module lớn hoặc thành phần chức năng chính, có thể triển khai riêng. Frontend, Backend, AI Service, Database, API Gateway, Authentication Service.
Interface Điểm giao tiếp giữa component; gồm provided interface và required interface. REST API, inference API, auth API, storage API.
Subsystem Nhóm component liên quan thành một hệ thống con để dễ quản lý. ML subsystem, user management subsystem, data subsystem.
Port Điểm giao tiếp cụ thể của component, dùng để kết nối interface. HTTP port, gRPC port, model inference endpoint.
Relationships Association, composition, aggregation, constraint, dependency, links. Frontend phụ thuộc API Gateway; AI Service phụ thuộc Model Store.

Ký hiệu cần nhớ

Component

Hình chữ nhật đại diện cho module lớn.

Provided interface

Dịch vụ component cung cấp cho component khác.

Required interface

Dịch vụ component cần từ bên ngoài.

Port

Điểm giao tiếp cụ thể nơi interface được nối vào.

Khi đọc component diagram, ưu tiên hỏi: module nào tự chịu trách nhiệm, interface nào là hợp đồng giao tiếp?

Tại sao cần Component Diagram?

Kiến trúc tổng thể

Hiểu hệ thống ở mức module thay vì từng class nhỏ.

Phân chia module

Chia hệ thống thành phần độc lập, dễ thay thế và dễ quản lý.

Microservices

Thiết kế service boundary, interface và dependency giữa services.

Làm việc nhóm

Mỗi nhóm có thể sở hữu một component hoặc subsystem.

Tài liệu hóa

Lưu lại kiến trúc module để onboarding, review và bảo trì.

Giảm coupling

Nhìn rõ phụ thuộc bất hợp lý trước khi triển khai.

Khi nào dùng Component Diagram?

Thiết kế hệ thống lớn

  • Khi một class diagram không còn đủ để nói về kiến trúc.
  • Khi cần chia nhóm phát triển theo module hoặc subsystem.

Thiết kế hệ thống AI/phân tán

  • Khi có AI Service, data pipeline, model store, API gateway.
  • Khi thiết kế microservices hoặc hệ thống phân tán.

Cách vẽ Component Diagram

Bước Việc cần làm Câu hỏi kiểm tra
1. Xác định module lớn Liệt kê Frontend, Backend, AI Service, Database, Storage. Module này có trách nhiệm độc lập không?
2. Xác định interface Ghi rõ dịch vụ component cung cấp hoặc cần dùng. Component giao tiếp qua API/contract nào?
3. Xác định dependency Nối component theo quan hệ sử dụng/phụ thuộc. Dependency có tạo vòng lặp hoặc coupling quá chặt không?
4. Tối ưu kiến trúc Tách/gộp component, đặt boundary và interface rõ hơn. Kiến trúc có dễ triển khai, test, thay thế và scale không?

Ví dụ từ Lab 02: Component Diagram

Web Store gồm SearchEngine, Shopping Cart, Authentication, Inventory, Orders, Customers và Accounts.

Đọc component diagram mẫu

Nhìn module

  • Component là đơn vị phần mềm triển khai hoặc thay thế được.
  • Subsystem bao quanh nhóm component liên quan.
  • Tên component phản ánh trách nhiệm chính.

Nhìn interface

  • Interface cho biết component cung cấp hoặc cần dịch vụ gì.
  • Orders nối Inventory, Customers và Shopping Cart.
  • Accounts tách riêng khỏi Customers.

3.
Deployment Diagram

Deployment Diagram là gì?

Tổng quan
Deployment Diagram là sơ đồ UML dùng để mô tả hệ thống được triển khai trên đâu: server nào, cloud nào, container nào.
  • Thể hiện infrastructure.
  • Thể hiện hardware hoặc runtime node.
  • Thể hiện network và communication path.

Thành phần chính

Thành phần Mô tả Ví dụ
Node Nơi phần mềm chạy hoặc được triển khai. Server, mobile, browser, cloud VM, Kubernetes node.
Artifact Đơn vị phần mềm được triển khai lên node. Application, model, database, Docker image, WAR/JAR.
Communication Path Kết nối mạng giữa các node hoặc runtime environment. HTTPS, TCP/IP, gRPC, message queue connection.

Ký hiệu deployment cơ bản

Node

Server, browser, mobile device, cloud hoặc execution environment.

Artifact

File/container/model/database được deploy lên node.

Communication Path

Đường kết nối mạng giữa các node, thường ghi protocol.

Deployment diagram trả lời câu hỏi vận hành: artifact nào chạy ở đâu và nói chuyện qua đường mạng nào?

Component nói API/AI service là module; deployment nói container chạy trên node nào.

Tại sao cần Deployment Diagram?

Hiểu cách triển khai

  • Biết hệ thống chạy trên server, cloud, container hay thiết bị nào.
  • Biết artifact nào được đưa vào runtime nào.

Thiết kế hạ tầng

  • Thiết kế cloud và hệ thống phân tán.
  • Tài liệu hóa kiến trúc triển khai để vận hành và debug.

Khi nào dùng Deployment Diagram?

Triển khai AI/cloud

  • Khi triển khai hệ thống AI lên server hoặc cloud.
  • Khi có model artifact, database, object storage, API service.

Triển khai phân tán

  • Khi triển khai microservices.
  • Khi dùng Docker hoặc Kubernetes.
  • Khi cần mô tả network giữa node.

Cách vẽ Deployment Diagram

Bước Việc cần làm Câu hỏi kiểm tra
1. Xác định node Liệt kê browser, server, mobile, cloud VM, database server, Kubernetes node. Đây là nơi chạy phần mềm hay chỉ là module logic?
2. Xác định artifact Đặt application, model, database, Docker image, JAR/WAR vào node phù hợp. Artifact nào thật sự được deploy?
3. Xác định kết nối Nối node bằng communication path và ghi protocol nếu biết. Node giao tiếp qua HTTP, TCP, gRPC hay message queue?

4.
So sánh và thực hành

Component Diagram vs Deployment Diagram

Component Diagram

Tập trung vào cấu trúc logic và cách tổ chức của các thành phần phần mềm.

Deployment Diagram

Tập trung vào việc triển khai vật lý các thành phần đó trên node phần cứng hoặc runtime.

Bảng so sánh

Tiêu chí Component Diagram Deployment Diagram
Mục tiêu Mô tả cấu trúc phần mềm ở mức cao. Mô tả triển khai vật lý của hệ thống.
Cấp độ Mức trừu tượng cao. Mức trừu tượng thấp hơn, gần triển khai thực tế.
Tập trung Tổ chức logic và mối quan hệ giữa các component. Triển khai phần mềm trên phần cứng và node.
Thời điểm Thiết kế. Triển khai.

Thực hành 1: Component Diagram

Chọn hệ thống AI của nhóm bạn hoặc dùng ví dụ: hệ thống hỏi đáp tài liệu nội bộ bằng RAG. Vẽ component diagram ở mức kiến trúc.

Component cần có

  • Frontend / Web UI.
  • Backend API / API Gateway.
  • Auth Service.
  • RAG / AI Service.
  • Vector Database, Document Storage.

Cần ghi rõ

  • Interface giữa Frontend và Backend.
  • Dependency giữa AI Service, Vector DB và Storage.
  • Subsystem nếu nhóm các component AI hoặc data.

Thực hành 2: Deployment Diagram

Với cùng hệ thống ở thực hành 1, vẽ deployment diagram để mô tả module chạy trên node hoặc container nào.

Node cần có

  • Client Browser.
  • Cloud VM hoặc Kubernetes cluster.
  • Database node hoặc managed database.
  • Object storage hoặc model storage.

Artifact cần có

  • Frontend static app hoặc web container.
  • Backend/API container.
  • AI inference container hoặc model artifact.
  • Communication path có protocol: HTTPS, TCP, gRPC.

Yêu cầu nộp bài

Bắt buộc

  • 01 component diagram cho hệ thống đã chọn.
  • 01 deployment diagram cho cùng hệ thống.
  • Hai diagram phải map được component sang artifact/node triển khai.

Mỗi diagram cần kèm

  • 1-2 câu mô tả phạm vi hệ thống.
  • Danh sách component hoặc node chính.
  • Giải thích 2 interface/dependency hoặc communication path quan trọng.

Checklist tự kiểm tra

Component

  • Component có trách nhiệm rõ và đủ lớn không?
  • Interface/provided/required có ghi rõ không?
  • Dependency có chiều hợp lý không?
  • Có component nào đang ôm quá nhiều chức năng không?

Deployment

  • Node có phải nơi chạy phần mềm hoặc hạ tầng thật không?
  • Artifact/container/model có được đặt vào node không?
  • Communication path có protocol hoặc loại kết nối không?
  • Deployment có phản ánh được kiến trúc cloud/Docker/Kubernetes nếu dùng không?

Tổng kết Lab 06

Hôm nay cần nhớ

  • Component Diagram mô tả module phần mềm, interface và dependency.
  • Deployment Diagram mô tả node, artifact và communication path.
  • Component là góc nhìn logic; deployment là góc nhìn triển khai.
  • Hai diagram phải map được với nhau khi đi từ thiết kế sang vận hành.
