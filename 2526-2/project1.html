Bài tập lớn: Xây dựng và tích hợp ứng dụng AI

Viết mã ứng dụng, gọi AI API, tích hợp với hệ thống có sẵn và đóng gói thành Docker image.

Môn học: Thực hành phát triển hệ thống trí tuệ nhân tạo

Học kỳ: 2, 2025–2026

Trường Đại học Công nghệ, ĐHQG Hà Nội

I) Thông tin chung

Mục tiêu: mỗi nhóm chọn một trong ba kịch bản, xây dựng tối thiểu một giao diện dùng được, hoàn thiện ứng dụng trong khung mã nguồn được cấp, đọc cấu hình từ biến môi trường, gọi AI API, kết nối các service và tích hợp với một REST API có sẵn. Kết quả cuối cùng phải chạy bằng một lệnh: docker compose up -d --build.

Sinh viên thực hiện

  • Hoàn thiện logic và tối thiểu một giao diện dùng được trong thư mục src/.
  • Dùng biến môi trường trong mã nguồn.
  • Gọi AI API và API hệ thống có sẵn.
  • Lưu trạng thái/kết quả vào PostgreSQL.
  • Build, chạy, kiểm thử và đẩy image.

Sinh viên không phải thiết kế lại

  • .env và .env.example.
  • Dockerfile.
  • docker-compose.yaml.
  • Cấu trúc dịch vụ và cơ sở dữ liệu nền.
  • Quy ước cổng, health check và lệnh khởi động.
Nhóm và đăng ký: tối đa 4 thành viên. Hạn đăng ký đề tài: 31/7/2026. Mỗi nhóm đăng ký một kịch bản và mô tả ngắn dữ liệu/use case cụ thể.
Hạn nộp bài: hết ngày 15/08/2026.
Bảo mật: không commit API key, token hoặc mật khẩu thật. File .env do giảng viên cấp/dùng khi chấm và phải nằm trong .gitignore. Repo chỉ lưu .env.example.

II) Chọn một trong ba kịch bản

Cả ba kịch bản dùng chung kiến trúc và bộ Docker mẫu. Khác biệt nằm ở dữ liệu đầu vào, lời gọi AI và API hệ thống được tích hợp.

Kịch bản 1

Trợ lý phân loại yêu cầu hỗ trợ

Nhận nội dung ticket, dùng AI để phân loại phòng ban, mức ưu tiên, tóm tắt và đề xuất câu trả lời.

Tích hợp bắt buộc

  • Đọc ticket từ Helpdesk REST API.
  • Gọi text/LLM API để phân tích.
  • Ghi nhãn và bản nháp trả lời trở lại Helpdesk API.
  • Lưu lịch sử xử lý vào PostgreSQL.

Đầu ra tối thiểu

category, priority, summary, suggested_reply và trạng thái đồng bộ.

Kịch bản 2

Làm giàu danh mục sản phẩm bằng AI

Nhận ảnh sản phẩm, dùng Vision API để gợi ý nhãn, danh mục, mô tả ngắn và cảnh báo ảnh không phù hợp.

Tích hợp bắt buộc

  • Đọc sản phẩm/URL ảnh từ Catalog REST API.
  • Tải ảnh và gọi Vision AI API.
  • Cập nhật metadata trở lại Catalog API.
  • Lưu kết quả và lỗi vào PostgreSQL.

Đầu ra tối thiểu

labels, category, description, image_warning và trạng thái đồng bộ.

Kịch bản 3

Trợ lý xử lý biên bản cuộc họp

Nhận transcript, dùng AI để tóm tắt, trích xuất quyết định và danh sách công việc cần thực hiện.

Tích hợp bắt buộc

  • Đọc transcript từ Meeting REST API.
  • Gọi text/LLM API để phân tích.
  • Tạo action item qua Task REST API.
  • Lưu biên bản và trạng thái đồng bộ vào PostgreSQL.

Đầu ra tối thiểu

summary, decisions, action_items, người phụ trách và trạng thái đồng bộ.

Giới hạn phạm vi: không yêu cầu huấn luyện mô hình, Kubernetes, monitoring stack hoặc hệ thống phân quyền phức tạp. Redis, MinIO, Milvus, Nginx và RabbitMQ Management đã có sẵn trong bộ Compose; mỗi nhóm chỉ bắt buộc dùng các service cốt lõi được nêu ở phần yêu cầu. Nhóm tích hợp đúng toàn bộ service mở rộng được cộng điểm.

III) Công việc và yêu cầu kỹ thuật

1. Hoàn thiện ứng dụng

  • Bắt buộc có tối thiểu một giao diện web dùng được; chỉ có REST API, Swagger hoặc CLI không được tính là đã có giao diện.
  • Giao diện phải cho phép nhập/chọn dữ liệu, gửi xử lý, hiển thị trạng thái chờ, kết quả và lỗi dễ hiểu.
  • Luồng chính phải thao tác được hoàn toàn trên giao diện, không yêu cầu người chấm gọi API thủ công.
  • Có REST API rõ ràng; tối thiểu gồm GET /health và một endpoint xử lý chính.
  • Kiểm tra dữ liệu đầu vào; trả HTTP status code và thông báo lỗi phù hợp.
  • Không đặt API key, URL dịch vụ, mật khẩu, cổng hoặc timeout trực tiếp trong mã nguồn.
  • Kết quả AI phải được kiểm tra/chuẩn hóa trước khi gửi sang hệ thống đích.

2. Tích hợp AI API

  • Gửi đúng input theo kịch bản và đọc đúng cấu trúc response.
  • Cấu hình model, URL, token và timeout bằng biến môi trường.
  • Xử lý tối thiểu: timeout, lỗi xác thực, lỗi 4xx/5xx và response không hợp lệ.
  • Không ghi token hoặc toàn bộ dữ liệu nhạy cảm vào log.

3. Tích hợp hệ thống có sẵn

  • Gọi API nguồn để lấy ticket, sản phẩm hoặc transcript.
  • Gọi API đích để cập nhật kết quả AI hoặc tạo action item.
  • Dùng token và base URL từ biến môi trường.
  • Không gửi lại trùng dữ liệu khi người dùng bấm xử lý nhiều lần; dùng khóa nghiệp vụ/idempotency hợp lý.

4. Kết nối PostgreSQL

  • Kết nối bằng DATABASE_URL; trong container, hostname phải là db.
  • Lưu tối thiểu: ID bản ghi nguồn, input rút gọn, output AI, trạng thái đồng bộ, lỗi và thời gian xử lý.
  • Ứng dụng phải tự tạo bảng hoặc chạy migration khi khởi động.
  • Không lưu API key/token vào database.

5. Build và chạy bằng Docker Compose

  • Không sửa Dockerfile và docker-compose.yaml nếu chưa được giảng viên cho phép.
  • docker compose build app phải build thành công từ máy sạch.
  • docker compose up -d phải khởi động được toàn bộ stack mẫu; các service có health check phải đạt trạng thái healthy.
  • Dữ liệu PostgreSQL, MinIO, Milvus và RabbitMQ phải dùng named volume.
  • Image ứng dụng phải được đẩy lên registry theo tên trong biến IMAGE_NAME.

6. Service cốt lõi và service mở rộng

Cốt lõi bắt buộc: app, db, nginx và các AI/API bên ngoài. Giao diện phải được truy cập qua Nginx.

Mở rộng: redis, minio, milvus và rabbitmq. Nhóm có thể chọn service phù hợp với kịch bản.

  • Redis: cache kết quả, trạng thái tạm hoặc chống xử lý trùng.
  • MinIO: lưu ảnh, transcript hoặc file đầu vào/đầu ra.
  • Milvus: lưu và tìm kiếm vector embedding.
  • RabbitMQ: đưa tác vụ AI/tích hợp API vào hàng đợi và xử lý nền.
  • RabbitMQ Management chỉ dùng để quan sát queue; không thay thế giao diện ứng dụng.

FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1

WORKDIR /app

RUN addgroup --system appgroup \
    && adduser --system --ingroup appgroup appuser

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY src/ ./src/
RUN chown -R appuser:appgroup /app

USER appuser
EXPOSE 8000

HEALTHCHECK --interval=10s --timeout=3s --start-period=20s --retries=5 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"

CMD ["uvicorn", "src.main:app", "--host", "0.0.0.0", "--port", "8000"]

V) Quy trình build, chạy và kiểm tra

  1. Nhận starter repository và file .env từ giảng viên. Không đổi tên hoặc cấu trúc các biến.
  2. Chỉ hoàn thiện mã trong src/ và kiểm thử trong tests/.
  3. Kiểm tra cấu hình Compose: docker compose config.
  4. Build image từ Dockerfile mẫu: docker compose build --no-cache app.
  5. Khởi động toàn bộ hệ thống: docker compose up -d.
  6. Kiểm tra container và log: docker compose ps, docker compose logs app.
  7. Mở giao diện và kiểm tra health endpoint qua Nginx: http://localhost:8080, curl http://localhost:8080/health.
  8. Chạy ít nhất ba test case: thành công, dữ liệu sai và một dịch vụ bên ngoài lỗi/timeout.
  9. Đẩy image: docker compose push app.
  10. Kiểm tra lại từ image đã đẩy bằng cách pull/chạy trên máy khác hoặc theo hướng dẫn của giảng viên.
Điều kiện hoàn thành: trên máy chấm đã có Docker và file .env, giảng viên clone repo rồi chạy docker compose up -d --build; hệ thống phải tự build và khởi động, không cần sửa file hạ tầng.

VI) Sản phẩm nộp và trình diễn

1. GitHub repository

  • Repo của nhóm để ở chế độ private; tất cả thành viên là collaborators.
  • Cấp quyền đọc cho các tài khoản giảng viên: daovietanh190499, Toan-Nguyen26, anhsuplo-87, 20020054-spm, hphungg.
  • Đẩy đầy đủ source code, test, README và các file mẫu; không đẩy .env.
  • Lịch sử commit phải thể hiện đóng góp của các thành viên.

2. Docker image

  • Image tồn tại tại địa chỉ khai báo bởi IMAGE_NAME.
  • Tag nộp bài phải cố định, ví dụ v1.0; không chỉ dùng latest.
  • Image chạy được mà không mount source code từ máy host.

3. README.md

  • Tên kịch bản, bài toán, input/output và giới hạn.
  • Sơ đồ luồng: API nguồn → ứng dụng → AI → DB → API đích.
  • Danh sách biến môi trường và ý nghĩa; không ghi secret thật.
  • Lệnh build, chạy, xem log, dừng hệ thống và chạy test.
  • Ba test case minh họa và kết quả mong đợi.
  • Phân công thành viên và phần mã mỗi người phụ trách.

4. Demo

  • Build image trực tiếp bằng mẫu được cấp.
  • Khởi động hệ thống bằng Docker Compose.
  • Thao tác trọn luồng chính trên giao diện web tại http://localhost:8080.
  • Trình diễn một luồng thành công và một luồng lỗi.
  • Chỉ ra biến môi trường được đọc ở đâu và container app kết nối container DB như thế nào.
  • Chứng minh kết quả đã được gửi sang API hệ thống có sẵn và lưu trong PostgreSQL.
